# 项目选题说明

## 项目名称

桌游社活动管理与组队平台

## 目标用户

项目主要面向高校桌游社团成员、活动组织者和社团管理员。

普通成员希望能够方便地查看桌游和活动信息、报名参加活动；活动组织者需要发布活动并管理报名情况；管理员需要维护桌游和成员等基础信息。

## 优先实现的业务场景

本项目优先实现“桌游活动发布与报名”场景。

活动组织者可以创建一个桌游活动，填写活动名称、时间、地点和人数限制。普通成员查看活动后可以进行报名，系统记录报名信息，并根据当前报名人数判断活动是否还有剩余名额。

第 03 周完成工程起步；第 04 周实现活动发布、活动查询、报名和数据库持久化。

## 核心模型

### Activity

表示一次桌游活动，主要包含：

- 活动名称
- 活动时间
- 活动地点
- 人数限制
- 活动状态

### BoardGame

表示社团中的桌游资源，主要包含：

- 桌游名称
- 桌游类型
- 适合人数
- 当前状态

## Week 04 核心业务流程

组织者创建活动 → 成员查询活动 → 提交学号和姓名 → Service 检查活动存在、未开始、没有重复报名且仍有名额 → 保存报名记录 → 返回 201。

本周两个核心实体是 Activity（活动）与 Registration（报名）。一个活动对应多条报名，每条报名只属于一个活动，数据库通过 activity_id 外键关联。成员使用 memberNo（学号或社员编号）标识，姓名仅作展示。

Activity 包含名称、地点、开始时间与容量。Registration 包含关联活动、成员编号、姓名与报名时间。BoardGame 仍为后续计划模型，本周没有实现。

主要业务规则：报名人数不能超过活动容量；同一成员不能重复报名同一活动；活动开始后不能报名。规则统一在 ActivityService 中实现。报名事务先锁活动行，再检查重复和容量，避免并发超额；数据库复合唯一约束提供重复报名的兜底保护。

本周范围：实现活动与报名六个 REST 接口。暂不包含用户登录、角色授权、取消报名或桌游库存管理。课内第 11 题另提供 Course 模型、JPA 读写测试及查询接口。
